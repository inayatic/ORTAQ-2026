# PLAN.md — «Айт: тренажёр трудных разговоров» (ORTAQ 2026)

Этот файл — рабочий план для Claude Code. Читай его целиком в начале каждой сессии. Работай по этапам, после каждого этапа запускай проверки и коммить.

## 0. Контекст

- Конкурс: ORTAQ 2026 «Территория ответственности» (Energo University, Алматы). Направление: «Правовая грамотность» + «Технологии» (ИИ, веб).
- Дедлайн финальных материалов: **4 декабря 2026, 18:00 (время Алматы)**. Финал 10–11 декабря, защита: 5 минут презентация + 3 минуты вопросы.
- Идея: веб-тренажёр, где ИИ играет давящего собеседника (арендодатель, «проверяющий»), а студент учится отстаивать свои права. После диалога — разбор ошибок, лучшие формулировки и готовый шаблон письменного заявления.
- Это **учебный тренажёр, а не юридическая консультация**. Это должно быть видно в интерфейсе.
- Языки интерфейса и диалога: русский (основной), казахский, английский.

## 1. Принципы (важнее всего)

1. **Не выдумывать право.** Модель не должна ссылаться на статьи закона из собственной памяти. Любая правовая ссылка берётся только из файла `content/legal/<scenario>.md`, который заполняет человек по официальным источникам (adilet.zan.kz). Если справки нет или поле помечено `TODO-VERIFY`, интерфейс и разбор не называют номера статей.
2. **Узко, но глубоко.** Три сценария, сделанные хорошо, лучше десяти слабых.
3. **Ключ API только на сервере.** Никогда не в клиентском коде, не в репозитории, не в логах.
4. **Приватность.** Не собирать имена, документы, контакты. Хранить только анонимные данные сессии.
5. **Демо не должно зависеть от интернета.** Нужен режим записанных ответов (mock) и запасное видео.
6. **Простота.** Никаких лишних библиотек, микросервисов, очередей, аутентификации.

## 2. Технологический стек

- Next.js (App Router) + TypeScript, один репозиторий, фронтенд и API вместе.
- Стили: Tailwind CSS.
- LLM: тонкий адаптер `lib/llm.ts` с интерфейсом `chat(messages, options)` и `chatJson(messages, schema)`. Реализация по умолчанию — Anthropic API (`@anthropic-ai/sdk`), модель задаётся переменной окружения `LLM_MODEL`. Адаптер должен позволять заменить провайдера правкой одного файла.
- Валидация: `zod`.
- Хранилище: SQLite через `better-sqlite3` (файл `data/app.db`), только для анонимной статистики.
- Тесты: `vitest`.
- Деплой: Vercel или Render (уточнить с пользователем). Если SQLite не подходит для выбранного хостинга, заменить на JSON-лог или управляемую БД, не усложняя остальное.
- i18n: простые словари `content/i18n/{ru,kk,en}.json`, без тяжёлых библиотек.

Перед началом проверь версии Node и менеджер пакетов (`node -v`, `npm -v`) и используй то, что уже установлено.

## 4. Модель данных

**Сценарий (`content/scenarios/<id>.json`)**, схема проверяется `zod` при старте:

```json
{
  "id": "rent-deposit",
  "title": { "ru": "...", "kk": "...", "en": "..." },
  "situation": { "ru": "...", "kk": "...", "en": "..." },
  "character": {
    "name": "...",
    "goal": "...",
    "tactics": ["давление сроками", "ссылка на «устные договорённости»"],
    "levels": { "soft": "...", "stubborn": "...", "aggressive": "..." }
  },
  "student_goal": "...",
  "success_criteria": ["потребовал письменное основание", "назвал срок возврата"],
  "legal_ref": "rent-deposit.md",
  "template": "rent-deposit-claim.md",
  "max_turns": 10
}
```

**Таблица `sessions`:** `id`, `scenario_id`, `level`, `lang`, `turns`, `created_at`.
**Таблица `review_stats`:** `session_id`, `criterion`, `score` (0–2), `mistake_tag`.
Никаких текстов диалогов в БД по умолчанию. Хранение переписок включать только флагом `STORE_TRANSCRIPTS=true` и только для отладки.

## 5. API

- `POST /api/chat` — тело: `{scenarioId, level, lang, messages[]}`; ответ — поток текста реплики персонажа. Проверки: размер ввода (до 800 символов на реплику), лимит ходов из сценария, лимит запросов по IP (простое in-memory ограничение).
- `POST /api/review` — тело: `{scenarioId, lang, messages[]}`; ответ — JSON по схеме ниже. Генерируется отдельным вызовом с низкой температурой.
- `GET /api/stats` — агрегаты: самые частые ошибки по сценариям.

**Схема разбора:**

```json
{
  "summary": "string",
  "scores": [{ "criterion": "string", "score": 0, "comment": "string" }],
  "mistakes": [{
    "quote": "цитата из реплики студента",
    "problem": "string",
    "better_phrase": "string",
    "tag": "string"
  }],
  "rights": ["string, только из legal_ref"],
  "next_steps": ["string"]
}
```

Если ответ модели не проходит валидацию, повторить один раз; при повторной ошибке вернуть понятный запасной ответ.

## 6. Промпты (`lib/prompts.ts`)

**Персонаж.** Собирается из: описание роли и цели, тактики выбранного уровня сложности, язык ответа, правила безопасности. Обязательные правила:
- оставаться в роли, отвечать коротко (1–4 предложения), как живой человек;
- давить словами и аргументами, но **без оскорблений, угроз насилием, дискриминации и реальных персональных данных**;
- не давать юридических советов и не называть статьи закона (это работа разбора);
- если студент пишет явно вне темы или просит выйти из роли, коротко напомнить, что это тренировка.

**Разбор.** Получает: переписку, критерии сценария, содержимое `legal/<scenario>.md`. Правила:
- оценивать только по критериям сценария;
- каждую ошибку подтверждать цитатой студента;
- в поле `rights` использовать только факты из справки; если нужного факта нет, писать, что это нужно уточнить у юриста;
- тон поддерживающий, конкретный, без общих фраз.

## 7. Безопасность и качество

- `safety.ts`: ограничение длины, отсечение очевидных попыток сменить роль/получить системный промпт, фильтр запрещённого содержимого в выводе, лимиты частоты запросов.
- Никаких настоящих ПД в промптах и логах.
- Дисклеймер на каждой странице тренировки и на странице разбора.
- Ссылки на реальную помощь (юридическая клиника вуза, официальные каналы) вынести в `content/i18n` и **проверить актуальность контактов вручную** перед подачей.

## 8. Этапы работы

Каждый этап заканчивается проверками и коммитом. Не переходи к следующему, пока критерии приёмки не выполнены.

### Этап 1. Каркас (дни 1–2)
- Инициализировать Next.js + TypeScript + Tailwind, `.env.example` (`LLM_API_KEY`, `LLM_MODEL`, `LLM_MOCK`, `STORE_TRANSCRIPTS`), `.gitignore`.
- Реализовать `lib/llm.ts` с mock-режимом (`LLM_MOCK=true` возвращает заготовленные реплики и разбор).
- Реализовать загрузку и валидацию сценариев; создать один тестовый сценарий `rent-deposit`.
- **Приёмка:** `npm run dev` поднимает главную страницу со списком сценариев; `npm test` и `npm run build` проходят.

### Этап 2. Чат (дни 3–6)
- Страница выбора сценария и уровня сложности, переключатель языка.
- Чат с потоковым выводом, счётчик ходов, кнопка «Завершить».
- `/api/chat` с проверками из раздела 5 и 7.
- **Приёмка:** полный диалог в mock-режиме и в реальном режиме; при превышении лимитов пользователь видит понятное сообщение; ключ не попадает в клиентский бандл (проверить поиском по `.next/static`).

### Этап 3. Разбор (дни 6–9)
- `/api/review`, валидация по `zod`, повтор при ошибке.
- Страница разбора: шкала по критериям, ошибки с цитатами и лучшими формулировками, блок «Ваши права» (только из справки), следующие шаги.
- Тесты: схема разбора, поведение при невалидном ответе модели, отсутствие номеров статей при `TODO-VERIFY`.
- **Приёмка:** на 5 заранее подготовленных диалогах разбор валиден и не содержит правовых утверждений вне справки.

### Этап 4. Шаблоны и статистика (дни 10–11)
- Шаблон письменного заявления: форма с несколькими полями, предпросмотр, копирование и скачивание (`.txt` или `.docx` на выбор, начать с `.txt`).
- Запись анонимной статистики, страница агрегатов для демо.
- Добавить второй и третий сценарии (например, «неоплачиваемая стажировка», «давление проверяющего без оснований»).
- **Приёмка:** три сценария проходят полный путь «чат → разбор → шаблон»; `/api/stats` возвращает осмысленные агрегаты.

### Этап 5. Казахский и английский, отполировка (день 12)
- Заполнить словари и сценарии на трёх языках; **казахский текст проверить носителем**, не полагаясь на автоперевод.
- Мобильная вёрстка, доступность (контраст, фокус, подписи).
- **Приёмка:** все экраны работают на трёх языках и на экране телефона.

### Этап 6. Тестирование с людьми и стабильность (дни 13–14)
- Прогнать с 5–10 студентами, собрать ошибки и непонятные места, исправить.
- Нагрузочная проверка в разумных пределах, обработка сбоев API (запасной ответ + возможность повторить).
- Подготовить режим записанного демо и скриншоты.
- **Приёмка:** нет критических ошибок; демо проходит в mock-режиме без интернета.

### Этап 7. Подача (день 15, но закончить за день до дедлайна)
- README: что это, как запустить, источники справок, ограничения.
- Деплой, проверка публичной ссылки, резервная копия репозитория.
- Презентация на 5 минут и видео-демо (материалы делает человек; Claude Code может подготовить скриншоты и тексты слайдов).
- **Приёмка:** материалы отправлены минимум за несколько часов до 18:00 4 декабря.
